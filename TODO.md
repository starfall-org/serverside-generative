# TODO — Separate authentication for the embedded Generative web client

Date: 2026-11-26. Replaces the previous general web-client roadmap in full.
Scope: serverside-generative only; no Android/Kotlin changes.

## 1. Required behavior

- [x] Opening the embedded web UI at `/` enters the workspace directly when no web password is configured (the default). When a password is configured, show the workspace for a valid session or a normal password login screen. Never require a mobile pairing code or pairing command for normal web access.
- [x] Web password configuration is optional: accept a startup flag, an environment variable, or a password configured through a trusted local CLI/admin control path. Fresh installations have no password and no mandatory setup wizard. Do not allow visitors to set or reset the server password remotely.
- [x] Keep the browser signed in across page reloads and daemon restarts until session expiry, explicit logout, password reset or administrator revocation.
- [x] No-password mode is automatic when no web password is configured. Print a prominent security warning to stderr whenever `generative serve` starts with the web listener enabled and no password configured, including service logs. Do not prompt, block normal startup, or generate a default password. See section 5 for public exposure safeguards.
- [x] Keep existing mobile SSH/TCP pairing, HTTP/WS invitation URL/QR, SPKI validation, device credentials, bearer tokens, RPC v5 and streaming semantics unchanged.
- [x] Keep `/connect` compatible with existing mobile invitation URLs. Any transitional browser pairing/migration flow must be secondary and explicit, not the normal web login. Do not consume a mobile invitation merely because the URL is opened in a browser.

## 2. P0 — Identity, persistence and migration

- [x] Define a distinct, stable server-owned web workspace identity (single-owner web account initially). Browser sessions are separate credentials for that identity, not new chat owners. Logout, password changes and restart must not orphan or delete history.
- [x] Authorize web requests through the existing owner-scoped RPC dispatcher and conversation store, using an explicit server-resolved web principal. Never accept an owner ID supplied by the browser as authorization.
- [x] Do not grant web access to independently paired mobile identities or their chats. A shared web/mobile workspace requires a separate explicit access-control design.
- [x] Existing browser-paired history: preserve all existing paired identities and durable chat files. Design an explicit, authenticated migration/import path for a user who proves control of both the old browser pairing and new web account; preserve messages, versions, metadata, and conflict handling. No automatic cross-owner copy or deletion. If migration is not supported initially, explain how to retain access/export via the old authenticated flow.
- [x] Keep chat persistence unconditional. Temporary model/MCP runtime credentials remain RAM-only; stored server credentials remain encrypted. No storage-format migration solely for the web login.

## 3. P0 — Password configuration and authentication API

- [x] Add a separate web password configuration mechanism, e.g. `generative web password set`, `generative web password reset` and `generative web password unset` (proposed CLI names; follow existing CLI conventions). For persistent password administration, read the password via a non-echoing prompt or secure stdin. Never write plaintext to YAML, database, URLs, logs or output. Startup overrides are explicitly supported below.
- [x] Support simple startup overrides: `generative serve --web-password 'your-password'` or `GENERATIVE_WEB_PASSWORD='your-password' generative serve`. Use a distinct web-only flag and environment variable. The environment variable must also work when launching the daemon/service through its configured environment.
- [x] Resolve the effective password in this order: explicitly supplied `--web-password` > `GENERATIVE_WEB_PASSWORD` (if set) > persisted web password hash > no password. Reject explicitly empty flag/environment values with a clear nonsecret error rather than silently disabling protection. Use `generative web password unset` and remove startup overrides to intentionally return to no-password mode.
- [x] Startup overrides apply only to the running daemon; do not overwrite the saved administrative password. Hash the effective override in memory, avoid retaining plaintext unnecessarily, and do not echo the flag or environment value in errors, service status, logs, diagnostics or generated service files. Warn in CLI help that flags can expose passwords via process listings and shell history and environment variables may be visible to other privileged processes. Recommend a protected service environment or the interactive persistent-password command for production.
- [x] Bind browser sessions to the effective password/security-mode generation. On daemon restart with unchanged effective password and mode, retain valid sessions; when the effective password changes or a passwordless/protected transition occurs, revoke previous sessions and close old streams. Maintain a private salted verifier or equivalent safe generation record for restart comparison without persisting plaintext or overwriting the saved administrative password. Compare safely; a new random salt per startup must not invalidate unchanged sessions. Document that an active flag/environment override takes precedence over saved-password edits; do not imply a saved-password reset/unset changes the active override. Require removal/change of the override and daemon restart to change its effective password.
- [x] Persist only a salted, memory-hard password hash (Argon2id with reviewed parameters) in private server-owned storage. Use constant-time comparison, bounded input, secure file permissions, atomic writes and no plaintext recovery.
- [x] Do not repurpose legacy `--password`, `GENERATIVE_HANDSHAKE_PASSWORD` or `--allow-legacy-pairing`. They retain their existing mobile v4 migration semantics.
- [x] Proposed separate web endpoints: `GET /web/auth/status`, `POST /web/auth/login`, `POST /web/auth/logout` and optional session-management endpoints. Status returns only nonsecret password-required/session state, including the default no-password mode. Login/logout use JSON, explicit origin checks, safe generic errors and no-store headers.
- [x] Add throttling for failed login attempts, bounded request body, rate limits, safe audit events and no secret logging. Avoid permanent account lockout or trusting arbitrary forwarded IPs.
- [x] Password setup/reset/unset runs under authorized local CLI/control socket only; effective password/security-mode changes revoke all existing web sessions and terminate their streams, but do not revoke mobile pairing credentials. If a startup override is active, report that saved-password edits do not replace it until the override is removed; explicitly requested web-session revocation still works. Setting an effective password immediately disables no-password bootstrap; a startup override is applied before opening the web listener. Unsetting is an explicit admin operation with a security warning. No remote first-visitor setup or universal default password. Distinguish a genuinely unset password from unreadable/corrupt configuration; fail closed for configuration errors.

## 4. P0 — Browser sessions and API integration

- [x] Generate high-entropy opaque browser session IDs. Store only hashes server-side, with owner, creation time, expiry, last-used time and revocation state; use private persistent storage so valid sessions survive daemon restart. Bound session count and clean expired records.
- [x] Set a host-only HttpOnly cookie, Secure for HTTPS, SameSite=Strict or Lax with explicit CSRF protection, appropriate Path and lifetime. No session token in localStorage, sessionStorage, JavaScript, query strings or URL fragments. Document the isolated loopback HTTP exception; never apply it to remote HTTP.
- [x] Rotate session IDs on login, invalidate on logout/expiry/password reset, and terminate affected web streams. Separate idle and absolute expiry policy; remember-me extends lifetime only within a documented maximum.
- [x] Provide cookie-authenticated same-origin web RPC/events routes (e.g. `/web/rpc`, `/web/events`) that delegate to the existing v5 dispatcher and event transport logic. Keep all existing `/v1/*` endpoints, bearer checks and wire formats intact. Avoid duplicating the business logic; do not make cookies an implicit authentication alternative for mobile routes.
- [x] Apply CSRF defenses to every cookie-authenticated mutation (including login/logout): exact allowed Origin, same-origin request policy, CSRF token where appropriate, no permissive CORS, no side-effecting GET. Check Host/trusted proxy configuration to prevent DNS rebinding and forwarded-header spoofing.
- [x] Enforce HTTPS for remote web sessions; only explicit loopback development/local listeners may use HTTP. Trust forwarding metadata only from configured trusted proxies. Do not treat a reverse proxy's loopback socket as proof of a local browser.
- [x] Keep authenticated SSE/polling same-origin with cookies; no bearer exposed to the browser for web sessions. Validate session throughout long-lived streams, close on logout/revocation/expiry, retain request ID, event cursor, revision and restart-recovery semantics. Optional WSS must apply equivalent Origin/session checks.
- [x] Terminal/agent/tool access still requires existing server opt-in and authorization. Web login must not enable disabled native tools or bypass runtime/SSRF restrictions.

## 5. P0 — Default no-password mode and startup warning

- [x] Default configuration: web password unset, direct access on the existing default loopback listener (`127.0.0.1:7091`) with no login form, setup wizard or pairing. Do not require a separate auto-login flag for this default.
- [x] At every actual daemon startup with HTTP/web enabled and no effective password configured, print a warning to stderr (also visible in service logs): `WARNING: Web UI has no password. Anyone who can reach it may access your web workspace. Set one with: generative web password set`. Include the actual listener address and exposure guidance; do not print secrets. No warning when web is disabled or protected by a configured password. Service start/status commands should surface the warning when practical.
- [x] Establish the browser session automatically through the same session machinery with a same-origin protected bootstrap POST (proposed `/web/auth/bootstrap`). Do not issue mobile pairing credentials, weaken `/v1/*` bearer authentication, or bypass a configured password. Cookie/CSRF protections still apply, but they are not a substitute for a password.
- [x] Preserve the default loopback bind and validate Host/Origin; do not treat a loopback proxy upstream as proof of a local browser. Proposed safety guard: require an explicit admin opt-in (e.g. `--allow-public-web-without-password`) for passwordless non-loopback or reverse-proxy exposure. Without that opt-in, disable public passwordless web access (not the mobile API) and explain how to configure a password. With opt-in, emit an additional prominent warning. Keep remote HTTPS requirements and existing mobile listener behavior unchanged.
- [x] Document that anyone able to reach a passwordless web endpoint can access its web workspace; loopback is not OS-user authentication. Warn against proxying an unprotected listener and document limits of detecting proxy exposure. No-password mode must not bypass existing authorization or enable disabled terminal/agent tools.

## 6. P1 — Web UI and UX

- [x] Replace the default `PairPage` with a direct workspace entry in no-password mode or Generative password login when configured; preserve existing theme, language, responsive layout and accessibility.
- [x] At startup query web session status. Display loading, optional password login, invalid password, throttled, expired session or offline/reconnecting state; bootstrap automatically when no password is configured and show the workspace immediately for a valid session. A network outage does not imply logout.
- [x] Remove mobile pairing instructions, QR/code field and paired-secret storage from the ordinary web login flow. Keep legacy browser-history migration behind an explicit secondary path if needed.
- [x] Replace browser-side pairing/bearer renewal in ConnectionProvider and ApiClient with cookie session authentication for the web routes, using same-origin credentials and CSRF protection. Keep normal chat/provider/MCP UI, RPC contracts, transport recovery and per-chat state intact.
- [x] Settings: session status, password administration guidance and optional session revocation. Show a nonblocking warning when no password is configured; hide misleading login/logout controls in that mode. With password protection, logout differs from deleting a chat and mobile identity revocation; re-login restores the same history.
- [x] Clear runtime secrets, drafts/caches as appropriate and subscriptions on logout; ensure stale async requests cannot mutate a subsequent authenticated session. Coordinate logout across tabs.
- [x] Do not silently persist the web password, bearer token or temporary provider credentials.
